# 撤退支援ミッション

## 概要

最初の作戦として「撤退支援」を作る。損傷した友軍の機体を撤退ポイントまで逃がし、追撃してくる敵小隊から守る。
離脱できた友軍の数で成功・失敗と報酬が決まる。Epic #682「作戦（ミッション）と敵小隊のロール」の Sub-Issue 4（Issue #686）の範囲を記述する。

敵を全滅させなくても勝てる作戦なので、殲滅向けの重い機体だけでなく、足止め・護衛・索敵に向いたビルドに出番ができる。
撤退ポイント・撤退ロール・作戦目標・作戦ルームの仕組みは既存のもの（[mission-rooms.md](mission-rooms.md)、[battle-engine-feature.md 36・37章](battle-engine-feature.md#36-作戦目標epic-682-sub-issue-1)）を使い、追加した仕組みは次の4つだけ。

* 作戦目標 `RETREAT_SUPPORT`（`RetreatSupportObjective`）
* 作戦マスターの1機の定義に、開始時の HP・欠損部位・武器種別を書けるようにした
* 達成度の内訳を `BattleResult.objective_detail` に保存する
* 報酬を離脱数に応じて段階的に出す

## 作戦マスター

定義は `backend/app/services/retreat_support_mission.py`（`build_retreat_support_mission()`、`missions.id = 4`）。

| 項目 | 内容 |
|---|---|
| 友軍 | 3 機（撤退ロール `WITHDRAW`）。機体マスター `gm`。HP の 40% / 55% / 35% で開始し、1 機は左腕、1 機は右脚が欠けている。撃ち返さない（`hold_fire`）。最高速度は 35 m/s（追撃部隊は機体の既定の 80 m/s） |
| 追撃部隊 | 敵チーム 4 機。前衛（`VANGUARD`）1 機と後衛（`SNIPER`）1 機で 1 小隊を組み、2 小隊（`pursuit-1` / `pursuit-2`）。機体マスターはどちらも `zaku_ii`（ザク・マシンガン、射程 400m）。狙撃機は前衛の後方に位置取る（陣形、[battle-engine-feature.md 38章](battle-engine-feature.md#38-小隊の陣形epic-682-sub-issue-6)）。狙撃機の `priority` は `SUPPORT` で、同じ小隊の機体を直近に攻撃した機体を優先して狙う（支援ターゲット選択、[39章](battle-engine-feature.md#39-支援ターゲット選択-support--protectepic-682-sub-issue-7)） |
| 戦場 | 辺長 4000m（`layout.field_size`）。エリア収縮なし |
| 撤退ポイント | プレイヤーのチーム専用。友軍のスポーン位置から約 2500m 離す。撤退機の速さで約 70 秒かかる |
| 作戦目標 | `RETREAT_SUPPORT`、`params.required = 2` |
| 説明文 | 目的（2 機以上の離脱で成功、全員で報酬増）と、友軍が撃ち返せないこと、勝ち方のヒント（撤退機を狙う敵を射程の外から撃ち、狙いを引きつける）を出す |

プレイヤー機は友軍と同じスポーン領域（中心 x=2800、半径 150）に出る。追撃部隊は x=3700 付近（半径 100）から追ってくる。
2 つの領域の縁どうしは 650m 離れていて、追撃部隊（`zaku_ii`）の射程（400m）と索敵範囲（500m）の外から始まる。
機体の値は機体マスターに揃えた（[機体マスター・エースの参照](#機体マスターエースの参照issue-719)）。追撃部隊の機体は、難易度の計測で決めた（[難易度の調整](#難易度の調整issue-711)）。

### 作戦マスターの定義の拡張

`MissionUnitConfig`（友軍・敵機の1機の定義）に次を足した。省略した値は今までと同じなので、既存の3件は変わらない。

| 項目 | 説明 |
|---|---|
| `current_hp` | 開始時の HP。null は `max_hp`。部位の HP も同じ割合まで減らす |
| `missing_parts` | 開始時に欠けている部位（`ALL_PART_NAMES`）。無い部位は組み立て時に `ValueError` |
| `weapon.weapon_type` / `is_melee` / `fire_arc_deg` | 格闘機を書くための武器の項目。既定は射撃武器 |
| `max_speed` | 最高速度 (m/s)。null は機体の既定値（Issue #711） |
| `hold_fire` | 撤退ロールのとき、敵に撃ち返さない。既定は false（Issue #711） |

`MissionLayout`（配置）には `field_size`（フィールドの辺長 (m)。null は参加機数から決める）を足した（Issue #711）。
スポーン領域と撤退ポイントは 0 から `field_size` の内側に置く。

### 機体マスター・エースの参照（Issue #719）

作戦の機体を、機体マスター（`master_mobile_suits`）かエースパイロット（`ace_pilots`）の ID で指定できるようにした。
作戦の機体を、プレイヤーの機体と同じ値の大きさ・同じ武器で出すため。機体マスターを直せば、作戦の機体にも反映される。
`MissionUnitConfig` に次を足した。`Mission` は JSON 列なので、マイグレーションは無い。

| 項目 | 説明 |
|---|---|
| `master_mobile_suit_id` | 機体マスター ID。`specs` の性能（HP・装甲・機動性・索敵・耐性・適性・補正・EN）・武器・地形適性と `weapon_slot_count` から機体を作る |
| `ace_id` | エースパイロット ID。敵機だけに置ける（友軍に置くと `ValueError`）。機体とパイロット（パイロット名・性格・戦術・懸賞金）を、`MatchingService.build_ace_mobile_suit()` と同じ値で作る |
| `current_hp_ratio` | 開始時の HP の最大 HP に対する割合（0 より大きく 1 以下）。部位の HP も同じ割合まで減らす。`current_hp` とは併用できない |
| `name` | 表示名。省くと参照先の機体名（機体マスターの `name`、エースは搭乗機の名前）。参照の無い機体は今までどおり「ザクII」 |

* `ace_id` と `master_mobile_suit_id` を両方書くと、機体だけを機体マスターに差し替える。パイロット・性格・戦術・懸賞金はエースのまま
* 作戦側で上書きできるのは、表示名・開始時の HP（割合）・欠損部位・ロール・小隊・最高速度・`hold_fire`。欠損部位は、機体マスターで欠けている部位に足す
* 機体マスターの武器は `MobileSuitService.create_npc_mobile_suit_from_master()` と同じ扱いにする（共通の `master_mobile_suit_fields()`）。武器マスターにある武器だけ `master_weapon_id` を持つ
* 参照を書いた機体では、直書きの値（`max_hp` / `armor` / `mobility` / `terrain_adaptability` / `weapon`）を使わない。直書きの値は、参照の無い既存の作戦（ID 1〜3）の読み込みにだけ残す。新しく作る作戦では使わない
* 参照先が無いときは、既定の機体にせず組み立てを `ValueError` で失敗させる

`app/services/mission_battle.py` は DB を使わないまま。参照先は呼び出し側が読み、`MissionMasters`（機体マスター ID → 機体マスター、エース ID → エースのマスター）として `build_mission_battle(masters=...)` に渡す。

| 呼び出し側 | 読み方 |
|---|---|
| 定期バッチ（`run_batch._process_room()`） | `load_mission_masters()`（`app/services/mission_master_loader.py`）で DB から読む。組み立てに失敗した作戦ルームは、警告を出して飛ばす |
| ソロミッション（`POST /api/battle/simulate`） | 同じく DB から読む。組み立てに失敗すると 500 |
| ローカルシミュレータ | `fetch` で読んでロスターの `master_mobile_suits` / `ace_pilots` に保存し、`run` はロスターから作る（[local-battle-simulator.md](local-battle-simulator.md#作戦の戦闘)） |
| `retreat_support_bench.py` | `--master-dir` の JSON（既定はテスト用の固定データ）から `mission_masters_from_data()` で作る |

撤退支援（`missions.id = 4`）は、友軍・敵機をすべて機体マスター参照に書き換えた（[作戦マスター](#作戦マスター)）。保存する定義は既定値を省いて書き出すので、直書きの値を持たない。
BattleViewer は作戦の機体を ID で描くため、表示名が機体マスターの名前のまま（同じ名前が並ぶ）でも描ける。

## 作戦の長さと配置（Issue #711）

作戦は「参加するプレイヤーが積極的に動かなければ負ける」難易度にする。
適当なビルドでなんとなく勝てると、ビルドの大事さが伝わらないため。撤退支援で機動・索敵寄りが勝つ筋書きは、遠距離攻撃をする機体（狙撃機）を倒すか、狙いを自機に向けさせることとした。

変える前は、次の理由でプレイヤー機のビルドが勝敗に効かなかった。

* 戦闘が 6〜12 秒で終わっていた。撤退機は約 7 秒で撤退ポイントに着き、プレイヤー機が撃てるのは 1〜2 発だった
* 敵のスポーン位置が撤退機から約 550m で、狙撃機（射程 600m）が開始直後から撃てた。撤退機の撃墜は開始から平均 2.6 秒で、すべて狙撃機によるものだった
* 撤退機が開始直後に格闘機を撃ち返していた。そのため狙撃機の `SUPPORT` の加点が撤退機にも付いていた
* 配置（x=-250、撤退ポイント x=-900）がフィールド（0〜2000m）の外にあった。境界の斥力が x の正の向きに働き、30 秒からエリア収縮も掛かる設定だった

次のように変えた。

| 変更 | 内容 |
|---|---|
| 作戦の長さ | 撤退ポイントを約 2500m 先に置き、撤退機の最高速度を 35 m/s にした（約 70 秒）。追撃部隊（80 m/s）は追いつける |
| 狙撃機の初期位置 | 狙撃機の射程と索敵範囲の外から追い始める。近づいてから撃ち始める |
| 撤退機は撃ち返さない | `hold_fire`（[battle-engine-feature.md 37.3](battle-engine-feature.md#373-撤退ロール)）。狙撃機の狙いを引きつけられるのは、追撃部隊を攻撃したプレイヤー機だけになる |
| 戦場の範囲 | 作戦の配置に辺長を持たせた（`MissionLayout.field_size` → `BattleField.field_size`）。指定するとユニット数によるフィールドの拡大・縮小をしない |
| エリア収縮 | 作戦の戦闘ではしない（`build_mission_battle()` が `BattleField.area_shrink` を false にする）。エリア収縮はバトルロイヤルで接敵させる仕組みのため。撤退支援より前の作戦（殲滅）にも同じく掛からない |

`BattleField` の `field_size` / `area_shrink` は既定値（null / true）のとき今までと同じ動きで、バトルロイヤルは変わらない。
ロールを持たない 2 / 8 / 20 機 × 撤退ポイントあり・なし × シード 1〜3 の 18 戦で、`main` とバトルログのハッシュが一致した（`seed_battle_rngs()`・ユニット ID・`PYTHONHASHSEED` を固定）。`engine_ci_smoke.py` も 9 ラウンド完走した。

## 作戦目標 `RETREAT_SUPPORT`

`backend/app/engine/objectives.py` の `RetreatSupportObjective`。護衛する友軍は、作戦マスターの `allies_config` から作った機体の ID を `build_objective(..., protected_unit_ids)` で渡す。

| 項目 | 内容 |
|---|---|
| 終了 | 友軍が全員「離脱（`RETREATED`）」か「撃破」になる。または敵が全滅する |
| 敵が全滅したとき | 戦場に残る友軍は離脱したものとして数え、終了する |
| 結果 | 離脱数が `required` 以上で `SUCCESS`、未満で `FAILURE`。最大ステップ数で打ち切ったときも、その時点の離脱数で判定する |
| プレイヤー機が撃破・離脱したとき | 作戦は続く。友軍が逃げ切れば成功（報酬は減る） |
| 達成度 | `ObjectiveResult` の `progress`（離脱数）/ `required` / `total`（友軍の数）/ `lost`（撃破された友軍の数）/ `player_survived`（護衛対象を除く自チームの機体が残ったか） |

## 達成度の保存

`BattleResult.objective_progress` / `objective_required` に離脱数と必要数、新しい `objective_detail`（JSON）に内訳を入れる。

```json
{ "total": 3, "lost": 1, "player_survived": true }
```

殲滅など友軍を数えない目標では null。

BattleViewer 用に、撤退ポイントと友軍のロールも同じ列に入れる（#687。[mission-frontend.md](mission-frontend.md)）。マイグレーションは `q2e3f4a5b6c7_add_objective_detail.py`（nullable の追加のみ）。

## 報酬

`PilotService.calculate_battle_rewards(win, kills, objective_result)`。`objective_result.total` が 1 以上の作戦だけ、離脱数に応じた報酬にする。それ以外は今までどおり勝敗と撃墜数で決める。

| 結果 | 経験値 | クレジット |
|---|---|---|
| 全員離脱 | 150 | 750 |
| 必要数を満たした | 100 | 500 |
| 失敗 | 20 + 離脱数 × 10 | 100 + 離脱数 × 50 |

* 成功してもプレイヤー機が撃破・離脱していたら、基本報酬を 0.7 倍にする（`ESCORT_PLAYER_DOWN_RATIO`）
* 撃墜ボーナスは殲滅戦の半分（`ESCORT_KILL_REWARD_RATIO`）
* 作戦に置いたエースを撃破すると、エースの懸賞金（`bounty_exp` / `bounty_credits`）を足す（`PilotService.calculate_bounty()`）。撃破の数え方は撃墜数と同じ（`compute_unit_kill_ids()`）。定期バッチとソロミッションの両方で払う。バトルロイヤルのエースには払わない（今までどおり）
* ドロップ（`DropScope.mission(作戦ID)`）は、成功したときだけ抽選する（既存の `is_win` の扱いのまま）

## 本番への反映

作戦マスターは DB が正本。`backend/scripts/maintenance/upsert_retreat_support_mission.py` で追加・更新する。

```bash
cd backend
uv run python scripts/maintenance/upsert_retreat_support_mission.py          # 差分の表示のみ
uv run python scripts/maintenance/upsert_retreat_support_mission.py --apply  # 書き込み（承認後に実行）
```

`--inactive` を付けると `is_active` を false で入れる。先にマイグレーション（`alembic upgrade head`）を当てること。
機体マスター参照に書き換えた定義（Issue #719）は、本番 DB に `gm` / `gouf` / `gelgoog` の機体マスターが要る（2026-10-25 に Read Only で確認済み）。

## 検証

`backend/scripts/simulation/retreat_support_bench.py`（DB 不要）で、同程度の戦力の4ビルド（殲滅向け・中間・機動/索敵寄り・足止め/護衛）を、撤退支援と、同じ友軍・敵小隊の殲滅戦で比べる。
足止め/護衛（`escort`）は射程 600m の武器を持ち、撤退機を攻撃する敵を優先して撃つ（`PROTECT`）。
殲滅向けに `PROTECT` を付けた `annihilator_protect` と、足止め/護衛を `CLOSEST` にした `escort_closest` も回す。成功率の差が機体・武器から来るのか、戦術から来るのかを分けて見るため（Issue #711）。
出撃なし（`absent`、開始時に HP 0）は撤退支援だけで回し、何もしなければ失敗する難易度かを確かめる。
成功率には 95% 信頼区間（Wilson）を付ける。既定は 100 ラウンド。

作戦の機体が参照する機体マスターは `--master-dir` の JSON から読む。既定はテスト用の固定データ（`tests/fixtures/master`）で、本番の値は `scripts/maintenance/export_master_data.py` で書き出して渡す。
ベンチのビルドの値は機体マスターと同じ大きさ（HP 750〜1200、威力 120〜240）にした（Issue #719）。
また `mobility` は回避にしか効かず、移動の速さは `max_speed`（既定 80 m/s）で決まる。機動・索敵寄りのビルドも、移動は他のビルドと同じ速さになる。

射撃の制圧（[battle-engine-feature.md 40 章](battle-engine-feature.md#40-射撃の制圧issue-716)）は、既定で作戦と同じ係数で有効にする。
`--suppression off` で無効に、`--suppression penalty=0.3,dirs=all` のように係数を変えて比べられる。`--workers` で並列数を変える（既定は CPU コア数）。

```bash
cd backend
uv run python scripts/simulation/retreat_support_bench.py --rounds 60
uv run python scripts/simulation/retreat_support_bench.py --rounds 60 --suppression off
uv run python scripts/simulation/retreat_support_bench.py --rounds 60 --master-dir scripts/maintenance/output/master_data
```

## 計測結果

### 難易度の調整（Issue #711）

本番の機体マスター（2026-10-25 に `export_master_data.py` で Read Only で書き出したもの）で、追撃部隊の機体を選んだ。
撤退機・配置・必要数（2）は変えていない。

#### 追撃部隊の候補

各ビルド 30〜40 戦（`seed` 1〜）。撤退支援の成功率。出撃なしはどの候補でも 0%。

| 前衛 × 狙撃 | 殲滅向け | 中間 | 機動・索敵寄り | 足止め/護衛 |
|---|---|---|---|---|
| `gouf` × 2 / `gelgoog` × 2（#719 の定義） | 0% | 0% | 0% | 0% |
| `gouf` × 2 / `gelgoog` × 1 | 3% | 7% | 3% | 0% |
| `gouf` × 2 / `zaku_ii` × 2 | 3% | 3% | 0% | 17% |
| `gouf` × 1 / `zaku_ii` × 2 | 32% | 22% | 5% | 38% |
| `dom` × 2 / `zaku_ii` × 2 | 12% | 15% | 5% | 28% |
| `zaku_ii` × 2 / `gelgoog` × 1 | 32% | 8% | 8% | 22% |
| `zaku_ii` × 2 / `zaku_ii` × 2（採用） | 40% | 17% | 10% | 47% |

* ゲルググ（ビームライフル 威力 280・射程 580m）が残ると、撤退機は 1〜2 発で落ちる。どのビルドでもほぼ成功しない
* グフ（格闘）が 2 機いると、プレイヤー機を落としてから撤退機を追う。撤退機への被害の約 8 割が格闘機になった
* 撤退機の HP を満タンにしても（`gouf` × 2 / `zaku_ii` × 2）、成功率は 12% 前後で変わらなかった。HP より追撃部隊の数と強さが効く
* ザク II 4 機にすると、追撃部隊の武器（射程 400m）より長い射程で撃てる足止め/護衛が最も高くなる

#### 採用した定義（ザク II 4 機）

3000 ステップ、150 ラウンド、`seed` 1〜150、射撃の制圧あり。括弧内は 95% 信頼区間。

| 目標 | ビルド | 成功率 | 平均離脱数 | 撃墜された友軍 | プレイヤー機の生存 | 平均の戦闘時間 |
|---|---|---|---|---|---|---|
| 撤退支援 | 殲滅向け | 24%（18〜31%） | 0.78 | 2.22 | 11% | 57.4 秒 |
| 撤退支援 | 中間 | 16%（11〜23%） | 0.50 | 2.50 | 4% | 54.5 秒 |
| 撤退支援 | 機動・索敵寄り | 12%（8〜18%） | 0.34 | 2.66 | 1% | 50.2 秒 |
| 撤退支援 | 足止め/護衛 | 43%（36〜51%） | 1.30 | 1.70 | 20% | 63.6 秒 |
| 撤退支援 | 殲滅向け + `PROTECT` | 21%（15〜28%） | 0.65 | 2.35 | 11% | 57.3 秒 |
| 撤退支援 | 足止め/護衛 + `CLOSEST` | 50%（42〜58%） | 1.49 | 1.51 | 23% | 65.7 秒 |
| 撤退支援 | 出撃なし | 0%（0〜2%） | 0.00 | 3.00 | - | 19.8 秒 |
| 殲滅戦 | 殲滅向け | 67%（59〜74%） | - | 1.99 | 54% | 133.8 秒 |
| 殲滅戦 | 中間 | 51%（43〜59%） | - | 2.25 | 35% | 127.2 秒 |
| 殲滅戦 | 機動・索敵寄り | 31%（24〜38%） | - | 2.55 | 21% | 108.5 秒 |

* 殲滅戦では今までどおり殲滅向けが最も高い（67%）。撤退支援と殲滅戦で、有利なビルドが入れ替わる
* 足止め/護衛の有利は、戦術（`PROTECT`）ではなく射程（600m）から来ている。`CLOSEST` にしても 50% で、殲滅向けに `PROTECT` を付けても上がらない（21%）
* 機動・索敵寄りは撤退支援でも最も低い。`mobility` は回避にしか効かず（1.6 と 0.9 の差は命中率で 7 ポイント）、索敵範囲の広さも勝ち筋にならない。HP と火力が低い分だけ不利になる
* 殲滅戦の時間切れは 17〜25%。作戦の戦闘ではエリア収縮をしないため、ベンチの殲滅戦でも決着しないことがある
* テスト用の固定データ（`tests/fixtures/master`）でも同じ傾向になる。撤退支援は足止め/護衛 45%（38〜53%）・殲滅向け 25%（19〜33%）・機動・索敵寄り 8%・出撃なし 0%。殲滅戦は殲滅向け 37%・足止め/護衛 31%・機動・索敵寄り 10%

機動・索敵寄りに勝ち筋を作る手段（ベンチで試した結果）:

| 最高速度を 110 m/s にする（機動を速さに効かせた場合の見積もり） | 18% | 25% |
| `SUPPORT` の加点（`SUPPORT_TARGET_SCORE_BONUS`）を 0.4 → 1.5 にする | 10% | 30% |

各 40 戦、ザク II 4 機の定義。どちらも殲滅向けに届かない。数値の調整だけでは機動・索敵寄りの勝ち筋は作れない。
