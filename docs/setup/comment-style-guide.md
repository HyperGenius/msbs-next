# コメントスタイルガイド

コードコメントの可読性とトークン消費を改善するための規約です。
実装前に必ず読んでください。

## 1. 書いてよいこと

判断基準は 1 つです。
「このコメントを消したら、読む人は何を失うか」。
失うものが無ければ消します。

コードから復元できない情報だけを書きます。

- なぜこの値・この順序なのか（例: `updated_at` ではなく `paid_at` を読むのは、返金でも `updated_at` が動くため）
- 何を変えると何が壊れるか（前提条件・不変条件）
- 外部ライブラリ・処理系の非自明な仕様、直感に反する挙動
- workaround を入れた理由と、それが不要になる条件
- 過去の障害から入れたガード（例: 二重計上を防ぐ）
- 従っている決定（ADR）への参照

## 2. 書かないこと

| 書かないもの | 例 | どこに書くか |
| :--- | :--- | :--- |
| コードの実況（WHAT） | `# ユーザー ID を取得する` の下に `user_id = get_user_id()` | コード自身 |
| 型注釈・引数リストのなぞり書き | 「`cart` は `Cart` である」 | シグネチャ |
| 作業経緯・変更履歴 | 「#312 で移設した」「旧実装では〜だった」 | Git 履歴・PR・ADR |
| issue / PR 番号、タスク ID | `issue #312`、`SHOP-1234` | Git 履歴・PR |
| 当たり前のこと | 「public なメソッドしか使えない」 | — |
| やらないことの列挙 | 「〜はここに宣言しない」 | ADR（意図的に外したなら） |
| 呼び出し元の説明 | 「呼ぶのは `CheckoutService.place_order()`」 | — |
| 継承先・別実装の説明 | 「継承したクラスが決める」 | ADR |
| 1 実装しか満たさない制約を抽象の不変条件として書く | 抽象の `authorize` に「与信はキューに積むだけ」 | その実装のクラス |
| 設計の弁護 | 「なぜこの実装が良いか」 | コミットメッセージ・ADR |
| コメントアウトしたコード | `# gateway.capture(order)` | Git 履歴（消す） |

## 3. コメントより先に直すもの

- 名前で説明できるならリネームする。裸の `-1` に意味があるなら、名前付き定数にする。
- 値ではなく定数名を引く。定数の横に実際の値を書くと、定数を変えた瞬間に嘘になる。
- 長い説明が要るなら、関数を分ける。説明したい塊は、たいてい名前を付けられる。

## 4. 形式（STE: Simplified Technical English）

- 1 文は 40 字前後で切る。長い文は 2 文に割る。
- 1 文に動作を 2 つ入れない。「A して B する」は 2 文にする。
- 結論を最初の 1 文に置く。前置き・例外は後に置く。
- 1 コメント 1 話題。
- 同じものを複数の言い方で呼ばない。
- 比喩・曖昧な修飾を使わない（「〜のようなもの」「事実上の」）。
- 文中の強調（`**…**`）を使わない。箇条書き見出しの太字は構造なので可。
- バッククォートはコード上の名前にだけ使う。ADR-0005 のような参照には付けない。
- 括弧で囲む。読点で挟まない。「A（B のとき）は C する」。

## 5. 分量と置き場所

- `#` コメントは 3 行以内。それを超える塊は、ファイル 500 行あたり 1 つまでを目安にする。
- コメントは直下のコードを説明する。`if` の上のコメントは、その分岐の説明として読まれる。位置の誤りはバグである。
- 日本語のコメントは文として書き、句点で終える（`#` も docstring も同じ）。行末の短い付記は句点を付けない。
- docstring は宣言の続きであり、宣言の言い換えではない。
  - 関数・メソッド・クラスは「何をするか」を述語で書く（例: 「注文をキューに積む。」）。
  - 属性・プロパティは名詞句でよい（例: 「引当済みの在庫数。」）。
  - `Args:` には型から読み取れないこと（符号の意味・単位・境界値）だけを書く。
  - `Returns:` には型ではなく、返る値が何を表すかを書く。
- 一時的なメモには `TODO:` を付け、コミット前に消すか issue にする。残すなら issue 番号ではなく、何が未解決かを書く。

## 6. 迷ったときの手順

1. 消してみる。読む人が何も失わないなら、そのまま消す。
2. 失うものがあるなら、それが「コードから復元できない情報」か確かめる。違うなら、名前・構造で直す。
3. 残すと決めたら、40 字前後の文に割り、結論を先に置く。
